# Асинхронный сервис процессинга платежей

Сервис принимает платёж через FastAPI, сохраняет его вместе с событием outbox
в PostgreSQL и асинхронно обрабатывает через RabbitMQ/FastStream. Один consumer
эмулирует шлюз за 2–5 секунд, сохраняет результат и отправляет webhook.
Идемпотентность защищает создание платежа, повторная доставка не проводит
завершённый платёж заново. Все HTTP-маршруты API защищены статическим ключом.

Consumer выполняет до трёх попыток с задержками 1 и 2 секунды, затем отклоняет
сообщение в DLQ. Бюджет сохраняется в БД и не сбрасывается при перезапуске.
Повтор webhook использует сохранённый результат и тот же идентификатор события.

## Запуск через Docker

```bash
cp example.env .env
docker compose --profile webhook up -d --build
curl -H 'X-API-Key: development-only-key' http://localhost:8000/healthcheck
```

Ответ healthcheck: `{"status":"ok"}`. Это проверка жизнеспособности API, а не
готовности PostgreSQL или RabbitMQ. Ключ берётся из `API_KEY` в `.env`.
Все HTTP-маршруты API, включая `/healthcheck`, `/docs`, `/redoc` и `/openapi.json`,
требуют заголовок `X-API-Key`. Для открытия Swagger в браузере нужно передавать
этот заголовок и при загрузке HTML, и при загрузке `/openapi.json`.

Compose запускает `db`, `rabbitmq`, `migrations`, `api`, `consumer` и тестовый
приёмник `webhook-receiver`. Если используется свой webhook, профиль `webhook`
можно не включать.
Миграции выполняются после готовности PostgreSQL; API и consumer ждут их завершения.
RabbitMQ Management: `http://localhost:15672`, пользователь и пароль берутся из `.env`.
Значения `payments` в примере предназначены для локальной разработки.
Данные БД и брокера сохраняются в именованных Docker volumes.

## Локальная разработка

Требуется Python 3.12+ и `uv`.

```bash
cp example.env .env
uv sync --frozen
docker compose up -d db rabbitmq
uv run alembic upgrade head
uv run uvicorn src.main:app --reload
```

В другом терминале:

```bash
uv run faststream run src.consumer:app
```

В `.env` хосты по умолчанию равны `localhost`. В контейнерах Compose подставляет
`db` и `rabbitmq` со стандартными внутренними портами. Если порты PostgreSQL/RabbitMQ
на хосте заняты, измените `DB_PORT`/`RABBITMQ_PORT` в `.env`: Compose использует их
для проброса портов, а локальные процессы — для подключения.

## Структура и транзакции

- `src/core` — конфигурация, логирование, общий lifecycle ресурсов.
- `src/database.py`, `src/dependencies.py` — async engine, фабрика сессий, зависимость FastAPI.
- `src/models` — модели `Payment`, `Outbox`, enum валют и статусов, базовая модель и timezone-aware даты.
- `src/repositories` — async-репозитории платежей и outbox без самостоятельного `commit`.
- `src/routers`, `src/schemas`, `src/services` — маршруты, контракты и сервис платежей.
- `src/messaging`, `src/consumer.py` — топология RabbitMQ, точка запуска FastStream и lifecycle publisher.
- `src/services/outbox.py` — фоновая публикация outbox с подтверждениями и повторами.
- `src/services/processing.py` — обработка платежа и доставка уведомления.
- `src/services/delivery.py` — устойчивое состояние попыток, повторы и завершение события.
- `src/services/gateway.py`, `src/services/webhook.py` — эмулятор шлюза и HTTP webhook.
- `src/messaging/payments.py` — единственный subscriber очереди платежей.
- `migrations` — создание таблиц (`0001`) и состояние обработки consumer в outbox (`0002`).

Границей транзакции управляет сервис через `async with session.begin():`.
Репозитории платежей и outbox получают одну и ту же сессию.
`get_db()` закрывает сессию, но не выполняет автоматический `commit`.
Для каждой независимой задачи consumer нужна отдельная сессия.
HTTP webhook выполняется после commit и освобождения блокировки платежа.
Во время локальной эмуляции шлюза (2–5 секунд, без сетевых запросов) строка
платежа блокируется, чтобы конкурентные дубли не запустили эмуляцию одновременно.
Внешняя служебная транзакция удерживает advisory-блокировку события до завершения
доставки. Она не блокирует строки, а изменения счётчика и результата фиксируются
отдельно. На время обработки используется дополнительное соединение PostgreSQL.

Сумма хранится в `NUMERIC` без заданной precision/scale и читается как `Decimal`.
CHECK-ограничения отклоняют неположительные/неконечные суммы и значения,
которым нужно больше двух знаков после запятой. Дополнительного максимума нет,
лишняя точность не округляется. Валюты и статусы ограничены PostgreSQL enum.

Для outbox предусмотрены уникальный `event_id`, связь с платежом, состояние
публикации, счётчик попыток и частичный индекс неопубликованных событий.

## Платёжный API

Примеры используют ключ из `example.env`. Подставьте ваш `API_KEY`, если он изменён.
Сумма передаётся строкой, чтобы сохранять точность денежных значений без
промежуточного преобразования в JSON float.

```bash
curl -i http://localhost:8000/api/v1/payments \
  -H 'X-API-Key: development-only-key' \
  -H 'Idempotency-Key: order-42' \
  -H 'Content-Type: application/json' \
  -d '{"amount":"100.00","currency":"RUB","description":"Заказ 42","meta":{"order_id":42},"webhook_url":"http://webhook-receiver:8001/webhooks/payments"}'
```

Ответ `202`: `payment_id`, `status`, `created_at`.

```bash
curl -H 'X-API-Key: development-only-key' http://localhost:8000/api/v1/payments/1
```

Ответ `200` содержит все поля платежа, включая сумму строкой с двумя знаками,
`processed_at` и даты создания/обновления. Неизвестный ID возвращает `404`.

Повтор создания с тем же ключом и теми же данными вернёт `202` с тем же ID
и текущим статусом. Суммы `"100.0"` и `"100.00"`, а также разный порядок ключей
JSON-объектов считаются одинаковыми. Изменение данных с тем же ключом вернёт `409`.
Параллельные запросы создают один платёж и одно событие outbox.

`Idempotency-Key` обязателен: 1–255 символов без пробелов. Отсутствующий ключ
или ошибки тела запроса возвращают `422`. `description`/`meta` можно опустить. 
Лишние поля отклоняются.
Отсутствующий или неверный `X-API-Key` возвращает `401` с разными машинными кодами.

Создание платежа не требует соединения с RabbitMQ: событие остаётся в БД до
подтверждённой публикации фоновым publisher.

## RabbitMQ и outbox publisher

`uv run faststream run src.consumer:app` подключается к брокеру, объявляет
обменники/очереди и запускает publisher. В Compose этот процесс находится
в сервисе `consumer`; отдельный контейнер для publisher не требуется.

Все обменники direct/durable, очереди classic/durable:

| Обменник | Routing key | Очередь |
| --- | --- | --- |
| `payments` | `payments.new` | `payments.new` |
| `payments.retry` | `payments.retry.1s` | `payments.retry.1s` |
| `payments.retry` | `payments.retry.2s` | `payments.retry.2s` |
| `payments.dlx` | `payments.dead` | `payments.dlq` |

Retry-очереди имеют TTL 1 и 2 секунды, после которого сообщение возвращается
в `payments.new`. `reject(requeue=False)` из основной очереди направляет
сообщение в DLQ после третьей технической ошибки. Невалидные события сразу идут в DLQ.

Publisher выбирает готовые неопубликованные строки через `FOR UPDATE SKIP LOCKED`.
На каждую публикацию используется отдельная транзакция и ожидание подтверждения
с тайм-аутом. Сообщения persistent; включены publisher confirms и проверка
маршрутизации (`mandatory` + `on_return_raises`). `published_at` записывается
только после подтверждения RabbitMQ.

При ошибке сохраняются `last_error` и время повтора. Задержки публикации:
1, 2, 4, 8, 16, 32, затем 60 секунд; число попыток не ограничено.
После восстановления брокера задача продолжает публикацию. При запуске с
недоступным RabbitMQ процесс ожидает подключения; API продолжает сохранять outbox.

Доставка в брокер at-least-once: при сбое между приёмом сообщения и commit БД
возможен дубль с тем же `event_id`/`message_id`. Стандартные TTL/DLX classic-очередей
используются без дополнительных гарантий переноса сообщений при сбоях кластера.

Параметры `.env`:

| Настройка | По умолчанию | Назначение |
| --- | --- | --- |
| `OUTBOX_POLL_INTERVAL` | `1` | Пауза между неполными циклами, секунды |
| `OUTBOX_BATCH_SIZE` | `100` | Максимум событий за один цикл |
| `RABBITMQ_CONNECT_TIMEOUT` | `5` | Тайм-аут попытки подключения, секунды |
| `RABBITMQ_PUBLISH_TIMEOUT` | `5` | Максимальное ожидание публикации/подтверждения, секунды |

## Повторы consumer и DLQ

Состояние обработки хранится в исходной записи outbox:

| Поле | Значение |
| --- | --- |
| `consumer_attempts` | Начатые попытки, от 0 до 3; сохраняется до обработки |
| `consumer_state` | `pending` → `processing` → `retry`, `completed` или `dead` |
| `consumer_next_attempt_at` | Минимальная дата следующей попытки для `retry` |
| `consumer_last_error` | Последняя ошибка consumer |

После первой ошибки сообщение отправляется в `payments.retry.1s`, после второй —
в `payments.retry.2s`. Сначала сохраняется план повтора в БД, затем выполняется
публикация с подтверждением RabbitMQ. Только после подтверждения исходному сообщению
отправляется `ack`. Отсутствие маршрута, Nack и тайм-аут публикации сохраняют исходное
сообщение через `nack(requeue=True)` с паузой 1 секунда. Повтор передачи в брокер
не запускает обработку ещё раз и не расходует дополнительную попытку.

Ошибки HTTP (включая `4xx`, редиректы и `5xx`), сети, тайм-ауты и технические
исключения обработки повторяются до трёх попыток всего. При ошибке webhook шлюз
повторно не вызывается. `failed` от эмулятора — финальный результат, для которого
также требуется webhook. Исчерпание попыток не меняет финальный статус платежа.
Если результат шлюза так и не сохранён, платёж остаётся `pending`, а событие — в DLQ.

После успеха сохраняется `completed`; повторное сообщение подтверждается без
шлюза и webhook. После третьей ошибки сохраняется `dead`, сообщение отклоняется
через DLX в DLQ. Старый дубль с `attempt=1` не обнуляет лимит. Если процесс прерван
посреди попытки, она считается израсходованной; после перезапуска назначается
следующая, а после прерванной третьей — DLQ. Автоматического сброса бюджета нет.

## Тестовый приёмник webhook

Consumer получает `payments.new` с `prefetch_count=1`. Для `pending` эмулятор
возвращает `succeeded` с вероятностью 90% или `failed` с вероятностью 10%.
`failed` — финальный результат, для него также отправляется webhook.
Статус и `processed_at` фиксируются до HTTP-запроса. Повторная доставка не меняет
статус, `processed_at` и `updated_at`. При необходимости повторной доставки
используется тот же `event_id`. После сохранения `completed` уведомление не повторяется;
если HTTP принят, но отметка не сохранилась, дубли уведомлений возможны.

Тело webhook:

```json
{
  "event_id": "fe292b6e-35be-4bf4-bcc8-e35b2a35609f",
  "payment_id": 1,
  "amount": "100.00",
  "currency": "RUB",
  "status": "succeeded",
  "processed_at": "2026-10-20T12:00:00Z"
}
```

Успешный ответ — любой `2xx`. Редиректы не выполняются. Общий тайм-аут
`WEBHOOK_TIMEOUT=5` секунд настраивается в `.env`. API-ключ сервиса не передаётся.
При ошибке webhook финальный результат остаётся в БД. Consumer выполняет два повтора
через 1 и 2 секунды, затем направляет сообщение в DLQ при третьей неудаче.

Отдельное приложение принимает произвольный JSON-объект на
`POST /webhooks/payments`, выводит его в лог и отвечает `204 No Content`.
Оно предназначено для локальных проверок доставки, не сохраняет уведомления
и не требует API-ключа платёжного сервиса.

Локальный запуск:

```bash
uv run uvicorn examples.webhook_receiver:app --host 127.0.0.1 --port 8001
```

Либо запуск через отдельный профиль Compose:

```bash
docker compose --profile webhook up -d --build webhook-receiver
docker compose logs -f webhook-receiver
```

Значение `webhook_url` для consumer, запущенного локально:
`http://localhost:8001/webhooks/payments`.
Для consumer в той же сети Compose:
`http://webhook-receiver:8001/webhooks/payments`.

Ручная проверка приёмника (тело приведено только как пример):

```bash
curl -i http://localhost:8001/webhooks/payments \
  -H 'Content-Type: application/json' \
  -d '{"event_id":"example-event","payment_id":1,"status":"succeeded"}'
```

Поле `webhook_url` использует тип `WebhookUrl` в `src/schemas/types.py`:
он проверяет HTTP/HTTPS URL с хостом без сетевых запросов.
